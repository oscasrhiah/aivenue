# 下一個大任務：工作流效率（速度與 token 成本）

狀態：**待辦**。等目前的「專案長期記憶第一階段」（docs/memory-phase1.md）完成後，才開始規劃與執行。
來源：使用者在 2026-11-04 提供的原始碼分析（外部 review）。內容是原始碼層面的判斷，尚未用實際工作流量測，不宣稱各項占多少比例。開工前要先核對下面引用的程式位置是否仍正確。

## 核心判斷

目前 Aivenue 預設讓每個角色**知道太多**、**重新理解太多**，而且讓一般任務**經過太多階段**。對中小型任務，協調成本可能超過實際寫程式的成本，所以使用者感受到「更慢、更燒 token」。單靠換便宜模型或加入長期記憶，改善有限；應先減少這三種成本，再用記憶降低跨工作流的重複探索。

## 七個問題與建議

### 1. 預設工作流太重（優先級最高）

- 現況：`packages/ui/src/components/RoleSettings.tsx`（約第 13 行）的預設同時開啟「計畫 → 計畫審查 → 實作 → 程式審查」，兩個階段各允許三輪，並開放 subagent；啟用獨立驗收還會再加一個階段。階段前後依賴，耗時相加，換不同模型也不會平行加速。
- 建議：提供三種明確模式，**預設輕量**。第一版由使用者選，不額外呼叫模型判斷複雜度；輕量模式的 executor 仍可在同一對話裡自行規劃。

| 模式 | 流程 | 適用 |
|---|---|---|
| 輕量 | 一個 executor 完成並驗證 | 小修改、一般除錯 |
| 標準 | executor → 一次獨立審查 | 一般功能 |
| 完整 | 計畫、計畫審查、實作、程式審查、必要驗收 | 跨模組、高風險 |

### 2. 共享上下文重複且與當前任務關聯不足

- 現況：`contextBlock`（`packages/core/src/context.ts` 約第 123 行）組合目前狀態與步驟、階段交接與上一個 agent 的 handoff、最近對話紀錄、整理後的知識、agent 清單、共享記憶、筆記、讀檔與指令活動；角色 prompt 又帶計畫、目標、實作摘要或前次問題。同一件事可能在計畫、筆記、交接、對話摘要中出現多次。有裁切與預算，但**裁切不等於去重，也不等於相關**。共享上下文預設上限是模型窗口的 50%（`orchestrator.ts` 約第 2630 行），大窗口模型會容許帶入大量歷史。
- 建議：
  - 「固定 token 上限＋角色需求」，模型窗口只當安全上限；先試每角色 4K～8K tokens 的額外共享資料上限（待驗證的起點），再依缺漏率調整。
  - executor：當前任務、必要計畫、未解問題、相關證據。reviewer：變更範圍、驗收條件、驗證結果。
  - 最近 100 筆對話改為按需查詢，預設不整批注入。
  - 同一筆證據只帶一份，其他區塊以 ID 引用。
  - 用適合語言與模型的 token 估算，不只靠字元乘除。

### 3. 預設每輪開新對話，反覆重建理解

- 現況：`ContextConfig.keepSessions`（`packages/core/src/types.ts` 約第 566 行）預設 false；`keepsSessions()` 在 `orchestrator.ts` 約第 663 行。作者或審查者下一輪通常開新對話，再帶入目標、計畫、交接與共享資料；修小問題也可能重新讀檔、重新理解架構。
- 建議（混合策略，**不要直接把 keepSessions 全面改成 true**——長 session 也會增加後續輸入量，要比較兩者實際成本）：
  - 同一角色短期返工時優先延續 session，只送新增問題、變更與必要狀態。
  - 歷史過大、方向改變或 provider 不支援時才開新 session。
  - 審查者與作者維持不同 session，保留獨立審查。
  - 沿用現有 resumed session 的共享資料增量機制。

### 4. 「先查紀錄」的提示反而增加固定工具往返

- 現況：共享提示（`context.ts` 約第 153 行）要求 agent 在執行指令、讀檔或調查前，查看共享內容並呼叫 `search_records`，可能變成「搜尋紀錄 → 判讀 → 仍需讀檔 → 執行原本工作」。
- 建議改為條件式：
  - 只有重跑昂貴測試、建置或長時間調查前，才優先找既有結果。
  - 一般短檔案讀取不強制先查紀錄。
  - 由系統直接提供「此命令已有可重用結果」的索引，重用判斷盡量交給系統。
  - 不把「曾經讀過檔案」當成其他 agent 已經理解該檔案。

### 5. 實作、審查、驗收的測試責任重疊

- 現況：`implementPrompt`（`prompts.ts` 約第 156 行）要 executor 跑 build/tests，有目標時自行量測；`codeReviewPrompt`（約第 176 行）又要 reviewer 執行可用的 build/tests；獨立驗收再量一次；UI 任務另有截圖要求。沒有返工也可能重複測試。
- 建議：建立可重用的驗證結果紀錄（命令、cwd、環境、相關輸入指紋、結束狀態、結果摘要、完整輸出位置）。reviewer 先判斷驗證是否充分；輸入與環境未變時重用一般機械檢查結果。以下情況才重跑：修改影響驗證輸入、證據不足或可疑、測試受外部狀態影響、明確要求獨立驗證。
- 與長期記憶的關聯：記憶第一階段的「證據事件／檔案指紋」機制（docs/memory-phase1.md §2–3）可以共用。

### 6. 返工後應只審查差異

- 現況：已有前次問題、作者回覆與「不要重複提出已解決問題」的提示（保留）。但 `describeChanges`（`orchestrator.ts` 約第 3748 行）主要給 `git status` 與 `git diff --stat`，沒有「上一輪審查版本 → 這一輪」的基準，新 reviewer session 容易重新探索整個修改範圍。
- 建議：
  - 每輪保存審查基準（含未提交與新增檔案），下一輪提供相對該基準的差異。
  - 主要審查未解問題、這輪修改及受影響範圍；大幅修改或架構改變時才擴大。
  - 設置階段 token／時間預算，不只用輪數控制成本。
  - 確認實際路由遵守「小問題不阻擋通過」。

### 7. 先讓成本可解釋，再決定怎麼壓縮

- 現況：有各 agent 的用量，但不足以回答「浪費在哪裡」。`organize`（librarian，`orchestrator.ts` 約第 3081 行）會把既有知識文件與新筆記一起送模型重整，這類維護呼叫也要單獨列出。
- 建議：每次呼叫記錄 Aivenue 組裝的 prompt 各區塊大小（目標與計畫、共享上下文、交接與歷史、Skills／工具描述、工具輸出），並按角色呈現輸入、快取輸入、輸出、可取得的推理用量與耗時。Aivenue 組裝的 prompt 估算要與 CLI 回報的整段 session 用量**分開顯示**，不能當成可完整拆解供應商內部成本。

## 建議的實作順序

1. 成本分解與固定任務基準。
2. 輕量／標準／完整模式，降低預設流程重量。
3. 縮小並依角色篩選共享上下文。
4. 短期 session 延續與增量審查。
5. 重用驗證結果，減少重複工具往返。
6. 最後讓長期記憶遵守同一份上下文預算（目前記憶第一階段已訂每次注入上限 1,500 tokens，屆時併入角色預算）。

## 驗收方式

用同一批固定任務比較「單 agent」「目前的 Aivenue」「改善後的 Aivenue」三組；模型、起始程式碼與驗收條件盡量一致。記錄：完成時間、各類 token（輸入、快取、輸出、推理）、成功率、遺漏的問題。實測照慣例只用 OpenCode 免費模型。

# 工作流效率改善：規劃

狀態：**A1／A2 已實作（只觀測）；A3 跑法完成；A4 第一次凍結（`frozen-20261104`）的基準作廢；完整基準重跑暫停，「容器化正式基準」改列為獨立待辦（§6），不再是改善工作流的前置條件**（2026-11-04）。作廢原因：免費額度在第 9 次用完卻被記成 stopped；OpenCode 的 session 位置都是啟動基準的資料夾而非 checkout，部分 agent 讀到隱藏測試與解答（詳見 `bench-results/frozen-20261104/report/INVALID.md`）。跑法已補上額度判斷、工作目錄與 PWD 隔離、以及 session 位置／基準資料夾／受保護檔案的檢查。凍結方式：`scripts/bench/freeze.mjs` 把工作目錄（含未提交與未追蹤檔案）複製到 `bench-results/<label>/source/`、保存 commit 與 `aivenue.diff`、在副本中建置並記錄 bundle 雜湊（`freeze.json`）；基準以副本的建置執行。`bench-results/` 不納入 git。問題來源見 `docs/next-task-workflow-efficiency.md`。本文件只描述要做什麼與如何驗收，**不宣稱能省多少**：後續的預設由階段 A 的資料決定。

## 0. 目標與原則

- 目標：中小型任務用 Aivenue 不應比「單一 agent」明顯更慢、更燒 token；大型、高風險任務保留多角色的品質優勢。
- **先量測再壓縮**：階段 A 只增加可見度與基準測試，不改任何行為。之後每個改動都用同一套基準比較前後。
- **品質不能默默變差**：基準同時看解題結果與審查能力（§2 A3）。省下的 token 若換來漏抓問題，報告上要看得到。
- **可退回、可對照**：行為改變都放在設定開關後面；另外凍結一份舊版程式與設定作為對照組（§2 A4）。
- 實測照慣例只用 OpenCode 免費模型（`opencode/deepseek-v4.1-flash-free`）。
- 專案長期記憶第一階段的剩餘驗收（畫面操作、Electron／VS Code／Linux、記憶開／關對照）**獨立追蹤**，不併入本計畫的驗收。

## 2. 分階段計畫

順序：**A1／A2 → A3 跑法 → A4 凍結舊版基準 → B → C（含原 F）→ D → E**。B 可以在 A3 跑法完成後開始開發，但改預設前必須先有可比較的基準結果。

### 階段 A：成本可解釋＋固定基準（不改行為）

**A1. 記錄每輪 prompt 的組成**
- 組 prompt 時記下各區塊的字元數與 token 估算：角色 prompt（細分目標、計畫、前次問題、實作摘要、變更清單）、共享上下文（細分到 `contextBlock` 每一區）、專案記憶、skills、附件、規則類文字。
- 這只說明「Aivenue 注入了什麼」，**不等於供應商實際計費的輸入**；兩者分開存、分開顯示，介面上不相加。

**A2. 成本欄位定義與分解**

先定義口徑，再做顯示：
- **互斥加總項**（相加＝該次呼叫的總量）：未命中快取的輸入、命中快取的輸入、輸出。
- **細分項**（只是其中一項的一部分，不可再加總）：推理 token 屬於輸出的一部分；快取寫入屬於輸入的一部分（有回報才顯示）。
- 逐一整理各解析器的實際口徑（Claude Code、Codex、Gemini、OpenCode、Copilot、Qwen…），在正規化層統一成上面的欄位；無法判斷的標「口徑未知」，不硬算。
  - 已整理（2026-11-04）：Claude Code 的輸入含快取寫入、不含快取讀取；Codex 的輸入含快取，換算時扣除，推理含在輸出內；OpenCode 的輸入、快取讀取、快取寫入分開回報，換算時把快取寫入補進未快取輸入；Gemini、Antigravity 看不出輸入是否已含快取，列在「拆分未知的輸入」，不放進未快取／快取兩欄，也不與它們相加。
- A1 的統計規則：每個區塊用自己的文字估算 token，整輪＝各區塊相加；共享上下文被截斷時只統計實際送出的部分，截掉的字元另外列出；每個 agent 保留最近 40 輪的逐輪明細，另存全程累計，成本分解用全程累計。
- **價格**：供應商沒回報價格時顯示「未知」，不是 0。免費模型的「價格 0」與「沒有耗用額度」分開標示（額度另看用量頁）。
- **時間**：分開顯示工作流實際耗時（牆鐘時間）、各 agent 耗時總和、等待時間（等使用者、等核准、等鎖、限流重試）。平行工作的 agent 時間不能加總成工作流耗時。
- 依角色、階段彙總；壓縮與知識整理單獨一列。
- **只用於觀測**：同時保留供應商原始欄位與換算後的欄位；既有的額度判斷、花費上限、路由與 agent 卡片既有數字一律不改，維持「階段 A 不改行為」。
- 介面：工作流 ⋯ 選單新增「成本分解」視窗；agent 卡片顯示該 agent 的花費（未知就寫未知）。

**A3. 固定任務基準（跑法）**

*任務與兩種能力分開評：*
- **解題能力**：3 個固定任務（小修改、一般除錯、跨兩個檔案的小功能），看最後測試是否通過、需求是否完成。
- **審查能力**：另給審查者**同一份事先準備好、含已知缺陷的 patch**，看能不能找出那些缺陷。解題任務中實作者提早修掉問題、審查者因而沒提，不算漏抓。

*隔離與固定條件：*
- 每次執行都用新的 checkout（從 fixture 複製）、新的 CLI session、隔離的 Aivenue 資料目錄。
- 效率比較的組別**一律關閉專案記憶**；記憶效果另外比較（屬於記憶第一階段的驗收）。
- 固定模型、推理設定、權限、可用工具與依賴版本，並記錄在報告中。
- 輪替三種設定的執行順序；記錄限流、重試與快取狀態。
- 模型不可用或被限流到無法完成時，該次標為**無效**並停止或略過，**不可默默換模型**。

*對照組：*
- **直接 CLI**：直接呼叫 OpenCode CLI 完成任務，不經 Aivenue。
- **Aivenue 輕量**：只有一個實作者（B 完成後才有；之前以「關閉計畫、不設審查者、不驗收」的設定代替）。
- **Aivenue 目前預設**：凍結版本（A4）。
- 分開列出前兩者，才能看出框架本身的成本。

*規模與定位：*
- 初步篩選：3 任務 × 2 次 × 3 設定＝18 次，三組固定為「直接 CLI、Aivenue 單實作者、凍結舊版」。
- 這 18 次是**初始基準**，不是整個計畫的總測試量。之後新增的組別（例如 B 的標準模式）與審查能力測試都另外計數，不可為了維持 18 次而替換掉對照組。
- 這個規模**只能發現明顯退步**，不能證明「品質沒有下降」。
- 改預設前的第二道門檻：針對差異最大、失敗或結果不一致的任務追加重跑，再做決定。

*報告*（JSON＋Markdown）：完成時間（三種時間）、A2 口徑的各類 token、花費（含未知）、成功率、審查能力測試的缺陷命中數、各區塊 prompt 大小排行、無效次數與原因、重跑間的變異。

*安全*：只用免費模型；跑法腳本沒有明確參數就不會啟動。

*實作*（`scripts/bench/`）：`fixture/` 示範專案（起始狀態可見測試全過）；`tasks.json` 三個任務；`acceptance/` 隱藏驗收測試（不會複製進 checkout）；`reference/` 正確解答（驗收測試在解答上全過、在起始程式碼上失敗）；`review/` 含三個已知缺陷的 patch 與比對規則；`run.mjs` 跑法（不加 `--go` 只列出計畫）。缺陷比對是啟發式（同一段同時提到檔名與關鍵字），原始審查內容留在 report.json 供人工確認。

*判定規則*：
- **結果分類**：pass（正常結束，且隱藏驗收與可見測試都通過）、fail（正常結束但有測試失敗）、timeout（到時間上限：算未解出，計入成功率分母，不排除）、stopped（工作流停下或在等人：同樣不算成功）、invalid（模型不可用、被限流或實際不是指定的模型：不列入比較）、error（跑法本身出錯）。
- **實際模型**：從 OpenCode 自己的 session 紀錄（`opencode session export <session id>`）讀出每則訊息的 provider 與 model 比對；是別的模型就整次無效，讀不到紀錄就標「模型未驗證」，不當成已確認。每個應有的 session 逐一記錄（直接 CLI：輸出中出現的所有 session id；Aivenue：每個實際執行過的 agent），缺 id 或讀不到紀錄的列為缺失；只要有缺失，最多只能是「部分驗證」。
- **逾時的用量**：保留逾時前已觀察到的用量並標「部分用量」；沒觀察到的顯示未知，彙總範圍時排除，不當成 0。
- **審查是否完成**：直接 CLI 要正常結束（結束碼 0）；Aivenue 刻意在第一份審查後停止，以「已提交審查」判定。`-free` 字尾只是名稱檢查，不代表價格。
- **期限**：每次執行一個期限，涵蓋啟動 hub、WebSocket、每個 RPC 與取消；期限後的清理另有最多 10 秒的寬限，實際花費記為 `cleanupMs`，不宣稱包含在期限內。不論成功、失敗或逾時，該次啟動的程序都會被結束，也不留下計時器。
- **審查不得改檔**：比較整個 checkout（排除 `.git`）的內容雜湊。
- **重現資訊**：報告記錄實際執行的 hub、bridge 與介面 bundle 的雜湊；A4 凍結時要從快照建置並記錄這些雜湊。
- 跑法本身有自己的測試（`scripts/test-bench.mjs`），用替身 CLI／hub，不呼叫模型。
- **位置驗證與模型驗證分開**：每個 session 各自記錄模型（符合／不符／缺失）與位置（在 checkout 內／外／未知）。沒有目錄欄位就是「未知」，不當成在 checkout 內。只有每個 session 的紀錄目錄都符合 checkout（報告欄位 `sessionDir = match`，「session 目錄符合」）的執行才計入比較；越界（`outside`）判為無效；未知的另外列出、不計入。逾時的執行在程序結束後，另用最多 2 分鐘檢查它已開始的 session。注意：`match` 只證明 session 紀錄中的位置，**不是**實際的存取邊界。
- **存取邊界（正式基準重跑前必須完成；見 §6 的獨立待辦）**：目前的工作目錄與 PWD 設定、事後檢查都只能「發現」越界，不能「阻止」agent 用絕對路徑讀取隱藏測試與解答或寫入原 repo。決定採用 **Docker 容器**：
  - 每次執行把 hub、CLI，以及 agent 能呼叫的工具（node、git、shell 等）一起放進容器。
  - 只掛載該次的 checkout 與必要的執行資源（例如唯讀的 CLI 安裝、可寫的暫存 home）；**不掛整個 repo 或任何上層資料夾**，因為掛載範圍直接決定容器能碰到哪些主機檔案。驗收、解答、缺陷規則與原 repo 都留在容器外。
  - 主機上的跑法收回 checkout 結果後，才在容器外執行隱藏驗收與缺陷比對。
  - 加一項不呼叫模型的測試：在容器內嘗試讀取外部解答、寫入原 repo，兩者都必須失敗。
  - 改用 Linux 容器後，三組對照（直接 CLI、Aivenue 單一實作者、凍結舊版）都要在同一個容器環境重新建立基準，報告標明是 Linux；不與 Windows 上的結果混合比較。
  - 前提：使用者自行安裝 Docker Desktop（2026-11-04 檢查：未安裝）。
  - 不採用的做法：只搬進 WSL 不算隔離，WSL 預設把 Windows 磁碟掛在 `/mnt` 下，仍讀得到原 repo；加密保存隱藏測試只能降低誤讀機會，原 repo、凍結副本仍有明文，而且同一個 Windows 使用者的程序之間沒有存取權限邊界，不能取代隔離。
- 審查能力測試裡，Aivenue 組別的實作者被要求不改程式；若改了，該次標為無效。

**A4. 凍結舊版基準**
- 在開始 B 之前，以目前程式與目前預設設定跑一次完整基準，存成對照組報告與設定檔，之後的比較都以它為準。
- 凍結內容要能重現**實際的工作目錄**，不只是 commit：保存原始碼快照或相對 commit 的完整差異（含未提交、新增的檔案）、設定、模型與工具版本、fixture 的指紋。不需要為此先替使用者 commit。

**A 的實作順序**：先做 A1／A2 的資料格式、記錄與成本視圖，並以測試確認 prompt 文字與派工結果都沒有改變；之後才做 A3 跑法與 A4 基準。

**A 的驗收**：能回答「多出來的 token 主要花在哪三類」；各家用量欄位口徑寫清楚；基準報告記錄重跑變異，不假裝穩定。

### 階段 B：流程模式（輕量／標準／完整）

- **流程模式**只決定角色配置，與後面的「效率設定」是兩個獨立維度（§3）。
- 每個模式都完整指定所有相關欄位，套用後不會沿用上次設定的殘值：

| 欄位 | 輕量 | 標準 | 完整 |
|---|---|---|---|
| 計畫階段 | 關 | 關 | 開（含計畫審查，3 輪） |
| 實作審查者 | 無 | 一位，最多 2 輪 | 一位，3 輪 |
| 目標驗收 | 關 | 關（可手動開） | 依使用者設定 |
| sub agent | 關 | 關 | 開 |
| 輪數上限 | 1 | 2 | 3 |

- 介面：新對話輸入框旁的模式選擇；套用後仍可微調，微調後顯示為「自訂」。
- **預設：標準**，只用在第一次使用或使用者沒有存過設定時；**不覆蓋**使用者已存的設定。
- 輕量模式的實作 prompt：沒有核准計畫時，請 agent 先寫幾行計畫再動手（不多開一個 agent），並自己跑測試。
- **驗收**：用 A3 比較輕量、標準與 A4 對照組；任何模式成為預設前，都要通過第二道門檻。

### 階段 C：依角色縮小並去重共享上下文（含記憶預算）

- 預算改成「固定 token 上限＋角色需求」，模型窗口只當安全上限；改用 `estimateTokens` 計算。起點：每個角色的額外共享資料 4K～8K tokens，依 A3 結果調整。
- **專案記憶併入角色預算**（原階段 F）：記憶不再有獨立的 1,500 tokens 上限，而是角色預算中的一個區塊，統一計算、統一顯示「未帶入」原因。
- 角色需求：
  - 實作者：目前任務、必要的計畫、未解問題、相關證據。
  - 審查者：變更範圍（見 D2）、驗收條件、驗證結果、未解問題。
  - 驗收者：目標與指標、驗證結果、變更範圍。
- 去重：角色 prompt 已帶的計畫、目標、實作摘要，不在共享上下文重複；同一份證據只帶一次，其他地方以 ID 引用。
- 最近 100 筆對話改為按需查詢（`read_context {topic: "log"}` 已存在），預設不整批放入。
- 「先查紀錄」改成條件式：只在要重跑昂貴的測試、建置或長時間調查前提醒。
- **驗收**：A1 的區塊大小下降；A3 解題成功率與審查命中數沒有明顯退步。

### 階段 D：短期返工延續對話＋只審差異

**D1 混合延續**
- 同一角色的短期返工優先延續原對話，只送新問題、變更與必要狀態。
- 對話已大（例如超過可用窗口的 40%）、方向改變或供應商不支援時，才開新對話。
- 作者與審查者維持各自的對話。新增審查者的短版「再審」prompt。
- 設定開放這個選項（目前 `keepSessions` 沒有介面）。
- 以 A2 實測比較「延續」與「重新交接」的成本，不先全面改預設。

**D2 每輪審查基準（逐行差異）**
- 審查當下保存**內容基準或可還原的版本**（例如在 git 中以不影響使用者分支的方式保存樹的快照，非 git 資料夾則保存變更檔案的內容副本），不能只靠目前只有路徑、大小、修改時間的 `snapshot`。
- 支援未提交、新增、刪除與重新命名的檔案。
- 下一輪的審查者（尤其是新對話）取得：**原任務的總變更摘要＋相對上一輪基準的本輪差異＋未解問題**，不能只看到本輪修補。
- 基準不完整或遺失時，**退回完整審查**，並在紀錄中說明。
- 大幅修改或架構改變時擴大範圍。

**D3 階段預算**
- 每個階段可設 token／時間預算，超過時像輪數上限一樣停下來問。

**D4 非阻擋建議**
- 先在審查 prompt 與結果格式中明確定義「可接受的非阻擋建議」（例如命名、風格、可選的重構），並讓審查者把這類意見分開列出。
- **不以程式把「只有 minor 的 revise」強制改成通過**；路由只依審查者的 verdict 與明確標示的阻擋問題。

- **驗收**：返工輪次的 token 與時間下降；A3 解題成功率與審查命中數沒有明顯退步。

### 階段 E：重用驗證結果

- 可重用的驗證紀錄包含：完整指令與參數、cwd、相關環境變數、測試設定檔、依賴鎖檔、工具版本、相關輸入的指紋、結束狀態、結果摘要、完整輸出位置。指紋沿用專案記憶的 `fingerprint`／`treeScan`。
- **只有系統親自觀察到的執行紀錄**可以重用；模型摘要裡說「測過了」不能升格成可重用結果。
- 以下情況一律不重用：掃描不完整、輸入在執行期間改變、背景指令尚未結束、結果依賴外部狀態（網路、時間、隨機、外部服務）、指令或環境有任何差異。
- 審查者先判斷既有驗證是否足夠；以下情況重跑：修改影響了驗證輸入、證據不足或可疑、明確要求獨立驗證。
- 系統直接提供「這個指令已有可重用結果」的索引，取代要求模型自己查。
- **驗收**：同一工作流內重複執行的測試／建置次數下降；審查命中數不因重用而下降。

## 5. 風險與防護

- **品質下降**：每階段都用 A3 的解題與審查能力測試檢查；明顯退步就不改預設，只留作選項。
- **延續對話反而更貴**：D1 以實測比較，不先全面改預設。
- **免費模型的雜訊與限流**：報告記錄變異與無效次數；結論以多次結果為準，限流造成的失敗不算進品質。
- **既有使用者的設定**：模式與新預設不覆蓋使用者已存的設定。

### 6.2 第一項改善：可選的「標準模式」（略過計畫階段）

*範圍*：標準模式是**可選**的流程模式：關閉計畫階段（計畫撰寫與計畫審查），保留程式審查（一位，最多 2 輪），不驗收、不開 sub agent。**既有設定與新對話的預設都先不變**。

*依據（只是優化候選）*：作廢基準中目前預設流程只有 2 次完整跑完（slug-maxlength、duration-units）。逐角色紀錄顯示計畫階段（計畫撰寫＋計畫審查）占 agent 時間約 249／361 秒與 97／168 秒，占供應商回報輸入（未快取＋快取）約 309k／735k 與 204k／682k。這兩次的 agent 可能讀過解答，樣本也只有 2 次，所以只說明計畫階段值得優先調查。

*預期影響（待驗證）*：
- 少開計畫撰寫與計畫審查兩個 session，會少掉這兩個 session 自己的探索與 Aivenue 注入的共享上下文。但**這不代表整個任務必然更省**：沒有計畫時，實作者可能多花探索，程式審查也可能抓到更多問題而增加返工，這些要一起算。
- 每個 session 的輸入有很大一部分是快取命中，快取輸入的計價與額度消耗不同於未快取輸入，不能把它直接說成「重付相同成本」；比較時未快取、快取、輸出分開看。
- 少了獨立的計畫審查，需求模糊或跨很多檔案的任務比較可能走錯方向，要到程式審查才被發現。
- 實作者沒有核准的計畫可依循，實作 prompt 要求先寫幾行計畫再動手。

*實作（2026-11-04）*：`packages/core/src/flowMode.ts`（`applyStandard`、`matchesStandard`、`flowModeOf`、`keepFlowMark`）；`WorkflowConfig.flow` 記錄設定來自哪個模式，沒有這個標記就是自訂，所以已存的設定即使配置相同也不會被當成標準模式。工作流設定視窗多了「流程模式：標準／自訂」，改了角色配置就自動變成自訂。實作 prompt 只在標準模式且沒有計畫時多一句「先寫幾行計畫」，其他配置的 prompt 一字不差。基準跑法多了可選組別 `aivenue-standard`，只在 `--configs` 指名時才跑，預設的三組不變；它的設定由核心的 `applyStandard` 從目前預設套用產生，不另外手寫，並有測試比對它和目前預設只差在流程欄位。新對話的預設（`defaultDraft`）沒有改。替身測試已涵蓋：欄位設定與殘值、自訂判斷、prompt、替身 agent 流程（只跑實作與程式審查、通過就完成、第 2 輪仍要求修改就停下來問）、跑法送出的設定。

*畫面操作（2026-11-04，暫存資料目錄，未呼叫模型）*：自訂 → 標準（計畫關、程式審查保留、輪數 2、驗收與 sub agent 關）→ 關閉後重開仍是標準 → 重新載入頁面仍是標準 → 輪數改成 3 變成自訂 → 關閉重開、重新載入都仍是自訂，存檔中的模式標記也已移除。過程中發現並修正一個原本就有的問題：頁面載入時若供應商清單比設定先到，會改用預設配置，之後使用者一改設定就把存檔蓋掉；現在會先向 hub 讀取存檔再決定（`Chat.tsx`）。修正前重新載入第一次就失敗，修正後連續 4 次都正確。另外注意到：自動指派的「目前會這樣分配」預覽，在計畫關閉時仍列出計畫角色（原本就如此，未處理）。

*驗證步驟（由小到大）*：
1. **替身測試（不呼叫模型，已完成）**：確認模式設定的每個欄位、套用後不沿用殘值、微調後顯示自訂、既有設定與預設不變；用替身 agent 跑一次流程，確認不會啟動計畫階段、實作後進入程式審查、最多 2 輪。

### 6.3 改預設前需要可信的品質證據

- 開發與上面的初測不需要額外的隔離環境：兩組暴露在同樣的環境，越界讀寫會經由 session 紀錄、基準資料夾名稱與受保護檔案雜湊被判無效。
- **把新對話預設改成標準模式之前，必須有可信的品質證據**。理由：這一步要靠「通過率沒有下降」把關；agent 若讀到參考解答，不論有沒有計畫階段都會通過，剛好會掩蓋拿掉計畫審查可能造成的品質下降；而且用相對路徑（例如 `../`）讀取時，紀錄中不一定出現基準資料夾的名稱，現有偵測抓不到。
- 取得可信證據需要讓 agent 實際上碰不到驗收與解答的執行方式；Docker 容器（§6.4）是其中一種。

### 6.4 獨立待辦：容器化正式基準

內容如 §2 A3「存取邊界」所述（只掛 checkout、容器外驗收、讀取外部解答與寫入原 repo 必須失敗的測試、三組在同一環境重建基準）。Docker 需由使用者自行安裝 Docker Desktop。完成後才重新凍結舊版並重跑完整基準。

### 6.5 C 的第一步：prompt 對話紀錄去重（2026-11-04，未呼叫模型）

*先分析：預設流程 executor 116 秒、標準模式 executor 64 秒（Codex 紀錄的任務起訖時間）*。資料來源是 Codex 自己的 session 紀錄（每次模型呼叫的時間與用量、每個工具呼叫的起訖）加上 Aivenue 存下的 prompt 區塊大小；只有各一次，以下是這兩次的現象，不是通則。

| | 預設流程 executor | 標準模式 executor |
|---|---|---|
| 模型呼叫次數 | 22 | 13 |
| 工具呼叫次數（執行工具的時間） | 21（約 23 秒） | 12（約 12 秒） |
| 其餘時間（大多是模型產生回應） | 約 93 秒 | 約 52 秒 |
| 第一次呼叫的輸入 | 20.8k tokens | 17.0k tokens |
| 全程輸入（其中快取） | 549.7k（529.8k） | 281.2k（248.4k） |
| Aivenue 注入的 prompt | 20,532 字元（共享上下文約 12.3k） | 5,393 字元 |

- **模型呼叫次數**：預設流程 22 次、標準模式 13 次，每次約 4 秒；工具本身只占兩成左右。呼叫次數和耗時相關，但上下文也會影響每一次呼叫的耗時，這兩次無法排除。
- **這兩次可辨認的差異包括進度回報與編碼返工；上下文對耗時的影響尚未分離。**多出的 9 次呼叫中可辨認的來源：
  - **逐步回報進度**：有核准計畫時，prompt 要求每個步驟開始與結束都呼叫 `report_progress`，預設流程呼叫 6 次，標準模式 2 次。

### 6.6 資訊正確性：輸出解碼與失敗的編輯（2026-11-04，未呼叫模型）

*亂碼在哪一層產生*。對照四個地方：

| 位置 | 「Café」 |
|---|---|
| 原始 fixture 檔 | 正確（UTF-8 `c3 a9`） |
| Codex 自己的 session 紀錄（planner 的 `Get-Content` 輸出） | 已是「Caf矇」 |
| Aivenue 存的事件 | 「Caf矇」，和 Codex 紀錄相同 |
| 共享上下文 | 「Caf矇」，和事件相同 |

- **原檔正確，是讀檔指令解錯**。Codex 在這台機器用 Windows PowerShell 5.1，主控台代碼頁是 950（Big5）。用已知內容的檔案（`中文測試 Café au lait 𝄞`，UTF-8 無 BOM）重現：

| 讀法 | 輸出用代碼頁 950 解回來 |
|---|---|
| PowerShell 5.1 `Get-Content`（預設） | `銝剜?皜祈岫 Caf矇 au lait ??`：讀檔時就把 UTF-8 當 Big5 解，`c3 a9` 變「矇」，就是這次的亂碼 |
| PowerShell 5.1 `Get-Content -Encoding UTF8` | `中文測試 Cafe au lait ??`：讀對了，但輸出到代碼頁 950 時 é 變 e、𝄞 變 ?? |
| PowerShell 7 `Get-Content` | 同上（讀對，輸出時有損失） |

- 之後的每一層（Codex 解讀 PowerShell 輸出、CLI 的 JSON、Aivenue 解析、紀錄、共享上下文）都如實傳遞，沒有再改壞。
- 這次執行裡，實作者把 `Get-Content -Raw` 讀到的錯誤字串寫回檔案，才真的改壞了測試檔（§6.5）。所以兩種情況都發生過：先是「原檔正確但讀錯」，接著因為寫回，變成「原檔被改壞」。

*Aivenue 自己的解碼層*：
- 讀 CLI 輸出用 `readline`，會正確處理被切在兩個 chunk 之間的多位元組字元。
- 有幾處是每個 chunk 各自轉成字串：`capture`（git 等指令）、`wait_for` 的檢查指令、hub 接收 bridge 送來的工具參數（例如中文的交接）、擴充套件安裝輸出、codex app-server 的回應。這種寫法遇到跨 chunk 的字就會變成 `�`；同一段輸出用舊寫法讀成 `������������ Caf�� au lait ����`。
- 已改成串流解碼（`setEncoding('utf8')`）。解碼用的編碼和原本一樣，只修正 chunk 邊界，**沒有全域強制 UTF-8**。

*測試（不呼叫模型，`scripts/test-workflow.mjs`）*：
- 端到端：假的 CLI 把 Codex 格式的 JSON 在每個多位元組字元中間切開、分次輸出，經過真正的 `runAgent` 與 Codex 解析器。確認保存的工具輸出與訊息和原文一字不差、沒有替換字元，下一個 agent 的共享上下文裡的讀檔內容與訊息也相同。
- `capture` 與 `wait_for` 的檢查指令遇到同樣切開的輸出，結果和原文相同。

*沒有處理、另外追蹤*：
- **PowerShell 5.1 讀檔的根本原因**：已加提醒（見下方「Windows 檔案提醒」）。
- **已處理：`wait_for` 檢查指令在 Windows 上的代碼頁**（見下方「檢查指令的輸出編碼」）。
- **已處理：agent 清單的「Files it changed」**（見下方「agent 的改動清單」）。

*失敗的編輯*（`ledger.ts` 的 `collectActivity`）：
- 過去只要分類是 edit，不論成敗都列進 FILES CHANGED，之前讀過的檔也會被標成「CHANGED since」。
- 現在依實際觀察標示：
  - 有任何一次成功的編輯，不論先後：列在 FILES CHANGED。
  - 只有失敗的編輯：列在 FILES POSSIBLY CHANGED，並說明失敗不能證明有沒有改到、需要確認。之前讀過的內容照樣顯示，但加上「possibly changed since … check it」；之前跑過的指令也加上同樣的提醒。
  - 壓縮後的「自己做過的事」也分成確定改動與可能改動。
- 測試：只有失敗、先成功後失敗、先失敗後成功三種情況，以及壓縮後的區塊。

*Windows 檔案提醒*（`prompts.ts` 的 `windowsFilesRule`）：
- 文案（prompt 以英文撰寫，意思同使用者提供的版本）：「WINDOWS FILES: when you read a file known to be UTF-8 with Windows PowerShell 5.1, use `Get-Content -Encoding UTF8`. For a partial change prefer `apply_patch` over reading the whole file and writing it back.」
- 只加在 Windows 上以寫入模式執行的 agent：實作者，以及以寫入模式啟動的 sub agent。計畫、計畫審查、程式審查、驗收等唯讀角色不加；其他平台回傳空字串，prompt 不變。
- 放在組合 prompt 的規則區塊，每份 prompt 只出現一次；接續同一段對話時不再重複（和背景工作規則相同）。
- 測試（不呼叫模型）：Windows 下完整流程只有實作者的 prompt 有這句，而且剛好一次；Linux 與 macOS 下所有角色都沒有；函式在非 Windows 平台回傳空字串。
- 這只是提醒，agent 是否照做、能不能減少編碼返工，要實測才知道。

### 6.7 待驗證的優化：降低進度回報頻率（先不做）

- **現況**：有核准計畫時，實作 prompt 要求每個步驟開始與完成時各呼叫一次 `report_progress`（`prompts.ts` 的 `implementPrompt`）。工具每次只更新一個步驟，並保存工作流狀態。所以 §6.5 初測裡預設流程的 6 次回報，至少有一部分是 Aivenue 明確要求的。
- **回報的用途**：
  - 步驟狀態會顯示在進度介面（`Progress.tsx`），也會帶進後續 agent 的共享上下文（`context.ts` 的進度區塊）。
  - 使用者追加需求、計畫更新時，程式會沿用相同 ID 與標題的步驟狀態。
- **少回報的代價**：進度更新變慢；工作流中斷時，可能少留一些完成紀錄。
- **目前無法判斷值不值得**：兩組各只跑一次，還混著編碼返工等其他差異，量不出逐步回報單獨花了多少時間。
- **決定**：保留現有工具與行為，先記為待驗證。
- **之後怎麼試**：
  - 等多次執行都看到逐步回報明顯占用呼叫次數或時間，再試最小改動：短步驟只要求完成時回報；長步驟在開始或遇到阻礙時仍立即回報。
  - 先用現有的 `report_progress` 驗證，再決定是否需要批次回報的 API。
  - 驗證時要一併確認：進度介面、後續 agent 的共享上下文、計畫更新時的狀態沿用，以及中斷後留下的完成紀錄，都沒有變差。

*檢查指令的輸出編碼*（`proc.ts` 的 `decodeShellOutput`，用在 `wait_for` 的檢查）：
- 依實際位元組解碼，不強制轉碼：輸出是合法的 UTF-8（git、node 等多數工具）就照 UTF-8；不是時，在 Windows 上用主控台代碼頁（`chcp` 取得，例如 950）解；代碼頁不明或沒有對應的解碼器，才和以前一樣照 UTF-8 解並出現替換字元。
- stdout 與 stderr 各自完整收集後再解碼，不會在 chunk 邊界斷字。合併時 stderr 在前、stdout 在後，讓 PowerShell 在最後印出的 False 仍判為檢查不成立；以前是依抵達順序交錯。
- 限制：PowerShell 5.1 在輸出時就會把代碼頁表示不了的字換掉（例如 é 變 e、𝄞 變 ??），這種損失無法在讀取端還原。
- 測試：解碼規則的單元測試（UTF-8、Big5、Windows-1252、代碼頁不明）；在 Windows 上實際用 PowerShell 5.1 輸出中文，檢查結果和原文相同，Test-Path 不成立仍判為失敗。

*agent 的改動清單*（`stats.filesChanged` 與新增的 `stats.filesMaybeChanged`）：
- 大多數 CLI 的解析器只在成功時回報改了哪些檔案；Codex 的 `file_change` 失敗時也會帶檔案清單，過去因此被列為已改動。
- 現在依該次編輯的實際結果分開記：成功的列在 `filesChanged`；只有失敗的列在 `filesMaybeChanged`，之後有一次成功就移到 `filesChanged`；先成功後失敗仍算已改動。
- 用到的地方都分開標示：Aivenue 代為整理的交接（「Files it possibly changed … check them」）、sub agent 回給上層的結果（`files_possibly_changed`）、不是 git 專案時的變更清單（加上「possibly changed」），以及介面上 agent 的檔案標籤與 agent 地圖（「可能改動」，虛線外框）。
- 越界改動的安全清單（`outsideChanges`）不變：失敗的編輯也列入，因為它可能已寫入一部分。
- 測試：替身 agent 經由真正的事件路徑回報「只失敗」「先失敗後成功」「先成功後失敗」三種編輯，確認統計與審查者 prompt 中的交接都正確區分。介面的顯示沒有在畫面上確認。
